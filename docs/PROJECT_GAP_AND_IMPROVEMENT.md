# 旅游小程序项目差距检查与改进建议

**生成日期：** 2026-04-28  
**检查范围：** `planning/`、`docs/`、`frontend/`、`backend/` 当前代码与文档  
**参考对象：** 携程、飞猪、同程、马蜂窝、小红书等旅游 App/小程序的主流体验趋势

---

## 1. 结论摘要

当前项目已经具备旅游行程规划小程序的 MVP 骨架：双入口首页、行程规划流程、随机玩流程、行程生成、保存、复制、分享、历史行程、后端 Fastify API、POI 与 AI 生成链路都已经落到代码层。

但与需求文档和优秀旅游产品体验相比，项目仍处在“可跑通主流程”的阶段，距离“真实、可执行、可信、可分享”的旅行工具还有明显差距：

1. **随机玩闭环不完整**：推荐结果页有“查看详情”按钮，但仍提示“详情开发中”；从推荐目的地生成行程的参数传递与结果页实际入口不匹配。
2. **登录与用户体系未形成闭环**：后端已有微信登录接口，前端历史行程依赖 `openid`，但未看到全局登录初始化流程。
3. **生产环境配置不足**：前端多处硬编码 `localhost`，`API_TEST_URL` 永远覆盖生产地址；随机玩输入页还直接请求高德 Web API。
4. **数据可信度不足**：行程结果缺少评分、营业时间、门票、拥挤度、评论数量、数据来源、更新时间等可信信息。
5. **体验与 UI 规范不一致**：需求和 UI 规范强调不使用 emoji、本地图片资源和清晰工具型布局，但结果页与随机玩页仍存在 emoji 和占位符式符号。
6. **竞品级能力缺失**：主流产品正在向“AI 行程助手 + 实时数据 + 预订/地图/分享闭环 + 当地问答”演进，本项目目前偏生成静态行程，缺少行中辅助、地图路线、分享海报、实时调整和内容可信验证。
7. **安全风险需要立即处理**：`backend/.env` 出现在工作区且包含真实服务密钥。虽然 `.gitignore` 已忽略 `.env`，仍建议立即轮换密钥并确认未被提交或泄露。

## 3. 需求差距明细

### 3.1 产品流程差距

**行程规划主流程基本完整，但缺少“可信落地感”。**

当前结果页能展示景点、美食、住宿和交通提示，但对用户来说仍像“AI 写出来的一份计划”。优秀旅游产品会给出更多可验证信息，例如：营业时间、门票、评分、评论数、预估排队、最佳到达时间、交通方式、是否适合老人/亲子、雨天替代方案、距离下一站的地图路线。

建议补齐：

- 每个行程项增加 `source`、`rating`、`review_count`、`open_time`、`ticket_info`、`last_verified_at`。
- 每天增加“路线合理性提示”：总通勤时长、步行强度、是否过度密集。
- 对 AI/模板兜底结果明确展示“数据完整度”，避免用户误以为全量真实验证。

**随机玩流程目前更像推荐列表，不是“灵感到出发”的闭环。**

需求文档要求 Top 3 推荐目的地，点击后展开完整行程。目前推荐卡片有摘要和生成按钮，但“查看详情”未完成，且“生成行程”跳转参数与结果页读取方式不一致。

建议补齐：

- `discover/result` 的“查看详情”直接展开推荐理由、适合人群、交通方式、预算拆分、推荐季节、风险提示。
- “生成行程”改为写入 `trip_params`，再跳转 `/pages/plan/result/result`。
- 后端补齐 `POST /api/discover/:destination_name/trip`，或删除文档中的该接口并统一复用 `/api/trip/generate`。

**我的页面目前只有历史行程，不足以支撑 v2 个性化。**

需求中“我的”包含偏好标签、历史、设置。当前只有用户信息与行程列表。

建议补齐：

- 用户偏好标签展示与编辑。
- 最近偏好、常去城市、收藏行程。
- 数据授权与隐私设置。
- 反馈入口：不准、太赶、预算不符、想换风格。

### 3.2 技术实现差距

**接口格式与文档不统一。**

API 文档规定统一返回 `{ code, message, data }`，但当前后端多处直接返回数组、对象或 `{ success, data }`。前端 `services/api.js` 做了兼容，但长期会增加维护成本。

建议：

- 新增统一响应包装层。
- 保留兼容期，但新接口全部返回统一格式。
- 更新 API 文档与真实路由参数，例如当前城市/区县接口实际是 `/cities/:provinceCode`、`/districts/:cityCode`，文档写的是 query 参数。

**环境配置不适合上线。**

当前 `frontend/constants/index.js` 中 `API_TEST_URL = 'http://localhost:3000'`，导致生产地址不会生效。`discover/input.js` 和 `discover/result.js` 绕过统一 API 服务直接写死 localhost。

建议：

- 增加 `env.js` 或构建时配置：`development`、`trial`、`production`。
- 所有请求统一走 `frontend/services/api.js`。
- 高德逆地理编码迁移到后端代理，前端只传经纬度。
- 清理前端硬编码 key、localhost、测试地址。

**密钥治理需要优先处理。**

工作区存在 `backend/.env`，其中包含高德、AI、微信等真实密钥。即使未提交，也应按泄露处理。

建议：

- 立即轮换高德、AI、微信密钥。
- 确认 `.env` 从未进入 Git 历史。
- 本地保留 `.env.example`，真实密钥进入部署平台 Secret 管理。
- 增加提交前 secret 扫描，例如 gitleaks。

**数据库与代码表名存在潜在偏差。**

文档和 `init.sql` 使用 `destination`、`poi_cache`，部分服务代码查询 `destinations`、`poi`。如果数据库适配层没有统一映射，随机玩和替换功能会出现环境差异。

建议：

- 统一表命名，或在数据库适配层集中处理兼容。
- 增加集成测试覆盖 SQLite 与 MySQL 两种配置。

### 3.3 设计体验差距

**当前视觉方向比初版需求更年轻，但部分细节破坏“工具型可信感”。**

页面已经引入城市背景和轻玻璃卡片，符合 2026-04-23 的视觉补充方向。但结果页使用 emoji 表达时间、门票、地址、预算、美食等信息，与“不得使用 emoji，使用本地图标资源”的规范冲突。

建议：

- 用本地小图标或纯文字短标替换 emoji。
- 结果页保持高信息密度：标题、地址、时长、价格、评分、交通分组展示。
- 降低大面积玻璃感卡片数量，结果页更像“路线清单/路书”，而不是营销页。

**随机玩输入页与行程规划页视觉语言不完全统一。**

行程规划页使用城市背景、hero、glass-card；随机玩输入页更像旧版表单卡片。

建议：

- 随机玩页也接入 `getCityBackground` 或独立探索背景。
- 预算、天数、偏好用同一套按钮、卡片、选中态。
- 位置选择抽屉加空态、加载态、错误态，避免“无数据时静默”。

## 4. 市场优秀产品启发

### 4.1 AI 行程助手正在从“生成攻略”转向“规划到落地闭环”

携程在 2025 年上线 AI 行程助手，强调一站式预订闭环、权威数据验证、自由编辑行程、订单同步、地图拖拽编辑和导出能力。参考来源：[新浪财经：携程正式推出AI行程助手功能](https://finance.sina.com.cn/roll/2025-09-17/doc-infqumnm2840270.shtml)。

对本项目启发：

- 不只生成文本行程，而要让用户能执行：路线、门票、酒店、餐厅、交通、预算都要可验证。
- 行程编辑不应只是删除/备注，应支持“换近一点”“换便宜一点”“换亲子友好”“今天下雨换室内”。
- 可以先不做真实预订交易，但要预留外链/跳转/复制信息位。

### 4.2 飞猪、同程、途牛等 OTA 都在做“AI + 实时价格/库存/预订”

公开实测报道显示，飞猪“问一问”具备交通、酒店、路线、预算、保障等助手角色，并可调用实时机酒价格；同程“程心AI”强调 AI + 实时预订、手绘行程图和多语言版本。参考来源：[新浪新闻：一键搞定攻略到预订？实测各路旅游AI助手](https://news.sina.com.cn/minsheng/2025-06-10/doc-inezqmne5704994.shtml)。

对本项目启发：

- MVP 可以先做“预算拆分”和“价格可信提示”，不必一开始接入交易。
- 分享能力要从普通小程序卡片升级为“行程海报/路线图”，更适合微信传播。
- AI 结果要展示调用依据，例如“按你选择的 1000-2000 元预算筛选”。

### 4.3 马蜂窝强调“当地指路人”和深度攻略

马蜂窝持续强化 AI 路书、当地指路人、行中服务和深度攻略能力，并公开提到 AI 旅行助手已生成大量深度旅行攻略。参考来源：[新浪财经：马蜂窝 AI 旅行助手相关报道](https://finance.sina.com.cn/stock/bxjj/2026-03-05/doc-inhpxfxv3261981.shtml)、[新浪财经：马蜂窝“旅游超级智能体”报道](https://finance.sina.com.cn/stock/t/2025-07-25/doc-infhrzcx1995541.shtml?froms=ggmp)。

对本项目启发：

- “行程生成后”应常驻一个轻量 AI 助手入口，回答当地问题。
- 增加“避坑/排雷”字段：不适合什么人、什么时候别去、是否商业化严重。
- 随机玩推荐要更像“当地朋友给建议”，不是单纯排序列表。

### 4.4 小红书式内容对用户决策仍有影响，但要注意可信与合规

用户习惯在小红书搜索旅行笔记、路线、拍照点和避坑经验。项目需求中有“小红书精选内容”作为 P2 数据来源，但爬虫和内容引用存在合规风险。

对本项目启发：

- 不建议 MVP 直接做爬虫内容集成。
- 可先做“用户可手动粘贴参考笔记/链接，AI 帮你转成行程约束”的功能。
- 后续若做内容聚合，应优先接入合规 API、用户授权内容或自有 UGC。

## 6. 建议的目标体验

### 6.1 行程规划目标体验

用户输入“成都 + 都江堰，3 天，带老人，不吃辣”，系统输出不应只是列表，而应是：

- 每天 3-5 个明确安排，带时间段、区域、交通方式。
- 展示“这天轻松/中等/紧凑”的节奏标签。
- 标明老人友好程度、步行量、是否需要预约。
- 每个地点都有可信来源字段：评分、营业时间、门票、地址、更新时间。
- 可以一键“换近一点”“换室内”“换不辣餐厅”。
- 可以生成微信分享图，朋友打开后看到完整行程。

### 6.2 随机玩目标体验

用户输入当前位置、2 天、预算 1000-2000、偏好美食和文化，系统输出 Top 3 不应只是城市卡片，而应是：

- 为什么推荐：距离、交通可达性、预算匹配、偏好命中。
- 适合什么人：亲子/情侣/朋友/长辈。
- 不适合什么情况：雨天、人多、预算不足、交通不便。
- 2 天预览路线：Day 1 / Day 2 的核心安排。
- 一键转完整行程。

### 6.3 我的页面目标体验

“我的”不只是历史列表，而是个人旅行资产：

- 历史行程、收藏行程、常用偏好。
- 最近喜欢的城市/偏好标签。
- 用户反馈记录，用于“越用越懂你”。
- 数据授权与清除入口。

### MVP 上线前

| 指标 | 目标 |
|---|---|
| 行程规划完整流程成功率 | ≥ 95% |
| 随机玩推荐成功率 | ≥ 95% |

## 9. 风险与注意事项

1. **合规风险**：小红书内容爬虫不建议作为 MVP 功能，优先使用用户授权输入或合规内容源。
2. **数据幻觉风险**：AI 生成的营业时间、价格、门票不能无来源展示，必须区分“实时验证”和“AI 建议”。
3. **性能风险**：小程序页面如果堆叠大背景、玻璃层、长行程列表，低端机可能卡顿；结果页应优先做列表虚拟化或按 Day 折叠。
4. **定位隐私风险**：随机玩定位需明确用途，并提供手动输入替代。
5. **交易闭环边界**：如果暂不接入预订，不要在文案上承诺“可预订”；可以先做“复制酒店名/打开地图/跳转外部小程序”的轻闭环。

## 10. 总体建议

这个项目的方向是对的：不要一开始做泛旅游社区，而是抓住“减少做攻略时间、输出可执行行程”这个高频痛点。下一阶段最重要的不是继续堆更多页面，而是把当前主流程打磨成可信闭环：

- **从“能生成”升级到“敢照着走”。**
- **从“推荐城市”升级到“解释为什么适合你”。**
- **从“静态行程”升级到“可修改、可分享、可验证”。**

优先把 P0 项做完，再做分享海报、地图路书、当地助手。这样既能保住工具型产品的清晰度，也能逐步接近市场上优秀旅游 App 的体验标准。
