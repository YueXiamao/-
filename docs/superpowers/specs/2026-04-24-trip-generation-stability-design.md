# 行程生成稳定性优先重构设计说明

日期：2026-04-24

适用范围：`v1`

关联产品文档：
- `planning/SPEC.md`
- `planning/ROADMAP.md`
- `planning/README.md`

---

## 1. 设计背景与问题定义

“生成行程”是整个小程序里最重要的主流程之一。用户在完成目的地、日期、天数、游玩方式、补充说明等参数选择后，点击“生成行程”，预期得到的是一份真实、可执行、可编辑的每日安排。

结合当前产品文档与现有实现，现阶段的核心问题不是单点 bug，而是整条生成链路还没有被产品化为一个稳定系统。当前链路更接近“参数 + POI + AI 一次性调用 + 模板兜底”，缺少中间质量控制层、分级降级机制和统一的用户态反馈。

当前主要问题包括：

1. 生成链路过短，没有中间验收层，任何一环波动都会直接污染结果。
2. “优先给出结果”的产品策略还没有真正落到系统设计里，当前 fallback 仍偏技术兜底。
3. 候选 POI 质量不稳定，直接影响后续生成质量。
4. 生成结果缺少结构校验，存在空内容、错误文案、占位词、异常字段直接进入前端展示的风险。
5. 前端生成状态过于粗糙，无法表达真实的多阶段处理过程。
6. 错误处理偏技术视角，缺少产品态分级反馈。
7. fallback 模板本身还不够像真实可用行程，用户体感容易把“已兜底成功”理解为“生成失败”。

一句话概括当前问题：

> 现在的“生成行程”还是接口调用流程，不是一个稳定、可校验、可降级、可观测的产品系统。

---

## 2. 方案选择与设计原则

本次确定采用：

**方案 2：稳定性优先的生成链路重构**

选择原因：

- 当前第一优先级是流程稳定性，而不是极限生成质量。
- 用户明确接受“优先保证有结果”，因此系统必须把降级路径做成正式产品能力。
- 相比最小修补，稳定性优先的重构能建立长期可维护的生成底盘。
- 相比重写生成引擎，当前范围更适合 `v1`，可以先稳住主链路，再逐步做质量优化。

本次设计遵循 4 条原则：

1. 先保结构，再保质量。
2. 先规则兜底，再 AI 增强。
3. 每一层都可单独失败，但不能轻易让整条链路失败。
4. 前端只接收产品态，不接收内部技术态。

## 3. v1 目标能力与边界

### 3.1 v1 目标能力

`v1` 重构后的“生成行程”必须具备以下能力：

1. **稳定生成**  
   用户填写完参数后，大多数情况下都能拿到一份结果；外部依赖失败时仍尽量返回可编辑结果。

2. **结构完整**  
   每天都有内容，景点/餐饮/住宿结构完整或按明确规则裁剪，不出现空天或不可展示行程项。

3. **结果可读**  
   地址、时长、预算、推荐理由、交通提示等关键信息可展示；不出现乱码、占位词、报错串入正文。

4. **失败可降级**  
   真实生成失败时，系统自动切换到“基础可编辑版”或“模板参考版”。

5. **状态可理解**  
   用户知道系统当前在做什么、当前结果是不是降级版、是否可以继续编辑或重试。

6. **链路可观测**  
   后端能分辨失败发生在哪一层，并记录降级命中情况与最低质量线是否满足。

### 3.2 v1 边界

本次重构明确不在 `v1` 内解决以下内容：

- 深度个性化推荐
- 协同过滤
- 分钟级路线最优规划
- 复杂交通网络调度
- 大规模人工精选内容运营系统
- 分享海报与精美导出
- 全城市高质量覆盖

### 3.3 v1 产品承诺

> 用户点击“生成行程”后，系统必须尽最大可能返回一份可看、可改、可继续使用的行程，而不是让用户面对报错、空白或明显失真的结果。

## 4. 稳定性优先的整体架构

本次重构将“生成行程”从一次性调用改造成分阶段流水线：

1. 请求接入与参数标准化
2. 候选 POI 准备
3. 候选质量预检查
4. 规则骨架生成
5. AI 内容增强
6. 结果校验
7. 分层降级与最终返回

核心架构结论：

> `规则骨架生成器 + AI 增强器 + 结果校验器 + 分层降级器`

其中：

- 规则骨架生成器负责稳定性底盘
- AI 增强器负责体验上限
- 结果校验器负责最低可用质量线
- 分层降级器负责“优先保证有结果”

### 4.1 架构原则

1. 先保证一定有一份完整可编辑的基础版。
2. AI 仅做增强，不承担从 0 到 1 造行程的唯一职责。
3. 所有结果返回前都必须经过统一校验。
4. 降级是正式产品能力，不是隐藏技术 fallback。
5. 前端根据 `source / fallback_level / warnings` 承接不同结果态。

### 4.2 推荐主链路

```text
用户提交参数
  -> 参数标准化
  -> 拉取候选 POI
  -> 候选质量预检查
  -> 规则骨架生成
  -> 尝试 AI 增强
  -> 校验增强结果
     -> 通过：返回增强版
     -> 不通过：回退骨架版
  -> 校验骨架版
     -> 通过：返回骨架版
     -> 不通过：回退模板版
  -> 校验模板版
     -> 通过：返回模板版
     -> 不通过：失败态
```

## 5. 核心模块拆分方案

### 5.1 后端模块

建议后端至少拆分为以下模块：

1. `TripGenerationController`
   - 接收请求
   - 基础参数校验
   - 调用编排器
   - 返回统一响应

2. `TripGenerationOrchestrator`
   - 整个生成流程总调度器
   - 控制阶段顺序、降级路径和最终结果返回

3. `TripCandidateService`
   - 拉取候选 POI
   - 分类、去重、过滤、统计覆盖度

4. `TripSkeletonBuilder`
   - 不依赖 AI 先生成一份可展示、可编辑的基础骨架

5. `TripAIEnhancer`
   - 基于骨架补描述、推荐理由、交通表达、摘要
   - 不改天数、不推翻骨架

6. `TripResultValidator`
   - 检查结构完整性、字段可展示性、内容最低质量线

7. `FallbackTemplateProvider`
   - 在极弱数据或骨架失败时，提供城市级基础模板兜底

### 5.2 前端状态模型

结果页不再只保留 `loading / error / success` 三态，建议使用：

```js
{
  phase: 'idle' | 'generating' | 'degraded' | 'ready' | 'failed',
  step: 'validating' | 'fetching_pois' | 'building_skeleton' | 'enhancing' | 'finalizing',
  errorCode: '',
  errorMessage: '',
  fallbackLevel: 'none' | 'rule_based' | 'template',
  trip: null
}
```

前端必须能区分：

- 正常生成结果
- 规则骨架版结果
- 模板兜底版结果

并分别给出不同提示。

### 5.3 数据结构建议

需要拆分 5 类对象：

1. `GenerateTripRequest`
2. `TripCandidateBundle`
3. `TripSkeleton`
4. `TripGenerationResult`
5. `TripValidationReport`

建议最终结果至少包含：

```json
{
  "trip_id": "T20260424XXXX",
  "title": "成都3日游",
  "source": "ai_enhanced",
  "fallback_level": "none",
  "destinations": [],
  "days": 3,
  "start_date": "2026-05-01",
  "itinerary": [],
  "generation_meta": {
    "used_ai": true,
    "used_rule_fallback": false,
    "used_template_fallback": false,
    "warnings": []
  }
}
```

## 6. 生成流程详细设计

### 阶段 1：请求接收与参数标准化

**目标：**  
把前端参数整理成统一的后端可消费请求对象。

**成功条件：**
- 参数完整
- 必填项有效
- 生成统一 `GenerateTripRequest`

**失败处理：**
- 直接返回参数错误
- 不进入生成链路

**降级策略：**
- 无降级

### 阶段 2：候选 POI 准备

**目标：**  
基于目的地、天数、偏好准备候选池。

**处理内容：**
- 拉取景点、餐饮、住宿
- 去重、过滤、分类
- 统计候选覆盖情况

**成功条件：**
- 拿到足够候选或至少拿到部分可用候选

**失败处理：**
- 标记覆盖不足，但不直接终止

**降级策略：**
- 带着 `coverage` 信息继续走

### 阶段 3：候选质量预检查

**目标：**  
根据候选池质量把请求分成 `strong / medium / weak` 三类。

**成功条件：**
- 能完成等级判断

**失败处理：**
- 不允许失败，至少要落入 `weak`

**降级策略：**
- `strong`：完整路径
- `medium`：受限增强
- `weak`：优先骨架或快速模板兜底

### 阶段 4：规则骨架生成

**目标：**  
在不依赖 AI 的情况下先拼出一版完整可编辑结果。

**成功条件：**
- 天数完整
- 每天非空
- item 类型合法
- 每项至少有 `type + name`

**失败处理：**
- 说明当前候选或编排规则不足以支撑基础版

**降级策略：**
- 直接进入模板兜底

### 阶段 5：AI 内容增强

**目标：**  
在骨架基础上补自然语言内容。

**成功条件：**
- 结构未破坏
- 描述更自然
- 关键字段更完整

**失败处理：**
- 调用失败
- 超时
- 解析失败
- 返回结构异常

**降级策略：**
- 直接回退骨架版

### 阶段 6：结果校验

**目标：**  
在最终返回前做统一验收。

**校验维度：**
- 结构完整性
- 字段可展示性
- 内容最低质量线

**成功条件：**
- 返回 `pass` 或 `usable_with_warning`

**失败处理：**
- 返回 `fallback_required` 或 `fatal`

**降级策略：**
- 增强版不通过 -> 回退骨架版
- 骨架版不通过 -> 回退模板版
- 模板版不通过 -> 失败态

### 阶段 7：分层降级与最终返回

结果分为 4 类：

1. 正常结果
   - `source = ai_enhanced`
   - `fallback_level = none`

2. 骨架降级结果
   - `source = rule_based`
   - `fallback_level = rule_based`

3. 模板降级结果
   - `source = fallback_template`
   - `fallback_level = template`

4. 最终失败态
   - 所有兜底都失败
   - 返回明确重试态

## 7. 异常场景矩阵与用户提示策略

### 7.1 设计目标

异常处理不再只区分“成功”和“失败”，而应分成：

1. **可静默修复**  
   系统内部处理，不打扰用户。

2. **可降级返回**  
   系统返回基础版或模板版，同时给用户可理解提示。

3. **可重试失败**  
   这次没拿到结果，但用户可以重试。

4. **不可恢复失败**  
   当前请求无法继续，需要用户修正输入或稍后再试。

### 7.2 异常场景矩阵

| 场景 | 所属阶段 | 内部处理策略 | 用户态结果 | 用户提示 | 可否重试 |
|---|---|---|---|---|---|
| 参数缺失或格式错误 | 参数标准化 | 直接拦截，不进入生成链路 | 失败 | 请完善出发日期、天数和游玩方式后再试 | 否，需先修正 |
| 目的地为空或目的地对象不完整 | 参数标准化 | 直接拦截 | 失败 | 请先选择至少一个有效目的地 | 否，需先修正 |
| POI 搜索超时 | 候选准备 | 记录超时，尝试部分候选继续生成 | 降级成功或继续生成 | 正在优先整理可用行程内容 | 是 |
| 目的地没有任何景点候选 | 候选准备 | 标记 `weak`，直接走模板兜底 | 模板降级 | 当前地区可用数据较少，先为你生成参考版 | 是 |
| 餐饮或住宿候选不足 | 候选准备 | 允许弱数据骨架生成，必要时复用或泛化候选 | 骨架降级 | 已为你先生成一版基础可编辑行程 | 是 |
| 候选池大量重复或空字段过多 | 候选预检查 | 过滤后继续，覆盖不足则降级 | 正常或降级 | 不单独提示，内部记 warning | 是 |
| 规则骨架生成失败 | 骨架生成 | 立即切换模板兜底 | 模板降级 | 当前条件下已先生成参考版行程 | 是 |
| AI 请求超时 | AI 增强 | 放弃增强，回退骨架版 | 骨架降级 | 已为你先生成基础可编辑行程 | 是 |
| AI 返回不可解析 JSON | AI 增强 | 放弃增强，回退骨架版 | 骨架降级 | 已优先返回基础版，你可以继续编辑 | 是 |
| AI 返回内容污染（带说明、报错、占位词） | 结果校验 | 校验不通过，回退骨架版 | 骨架降级 | 本次先生成基础版，推荐内容稍后可再优化 | 是 |
| 增强版结构不完整 | 结果校验 | 回退骨架版并记录结构问题 | 骨架降级 | 已返回稳定版行程，可继续调整 | 是 |
| 骨架版也不满足最低展示标准 | 结果校验 | 切模板版 | 模板降级 | 当前目的地数据不足，先给你一版参考行程 | 是 |
| 模板版缺失或模板损坏 | 模板兜底 | 返回最终失败态 | 失败 | 这次生成没有完成，请稍后重试 | 是 |
| 后端服务内部异常 | 任意阶段 | 统一异常封装，优先尝试兜底；兜底失败再报失败 | 降级或失败 | 系统正在恢复中，请稍后重试 | 是 |
| 前端拿到空 itinerary | 前端结果页 | 拦截展示，进入失败页并保留重试入口 | 失败 | 这次生成没有完成，请重新生成 | 是 |
| 网络请求失败 | 前端请求 | 展示失败态，支持重试 | 失败 | 网络异常，请检查后重试 | 是 |

### 7.3 用户提示分层策略

#### A. 加载阶段提示

用户在生成过程中应能感知当前阶段，建议按以下顺序展示：

1. 正在检查出行条件
2. 正在搜索景点与餐饮
3. 正在安排每日行程
4. 正在补充推荐内容
5. 正在整理最终结果

这些提示应配合阶段状态切换，而不是固定 loading 文案。

#### B. 降级成功提示

当系统已成功返回结果，但来源不是正常增强版时，需要明确提示来源和可继续操作能力。

**规则骨架版提示：**

> 已先为你生成一版基础可编辑行程，你可以继续调整顺序、替换内容或添加备注。

**模板版提示：**

> 当前目的地可用数据较少，先为你生成一版参考行程，后续可继续编辑完善。

提示形式建议：

- 结果页顶部轻提示条
- 不阻塞阅读
- 可收起

#### C. 最终失败提示

只有所有降级都失败时，才进入纯失败态。

建议文案：

> 这次生成没有完成，请稍后重试。

如果是网络原因，可以更明确：

> 网络异常，请检查后重试。

#### D. 参数错误提示

参数错误不要进入结果页报错，应在参数页原地提示：

- 请选择有效日期
- 请至少选择一个游玩方式
- 请先选择至少一个目的地

### 7.4 用户提示文案约束

为了避免技术信息污染用户体验，所有前端提示必须遵守以下规则：

1. 不暴露内部异常细节  
   禁止直接展示：
   - AI 调用失败
   - JSON 解析失败
   - provider timeout
   - fallback exception

2. 不把“降级成功”表达成“失败”  
   用户只要拿到了可编辑结果，就不应看到“生成失败”。

3. 不把明显质量问题当作正常成功  
   如果结果是骨架版或模板版，必须显式标识，而不是伪装成完整增强版。

4. 所有提示都应引导下一步  
   - 继续查看
   - 编辑调整
   - 重新生成
   - 返回修改参数

### 7.5 推荐的前端展示策略

建议结果页顶部根据返回态展示不同信息条：

#### `source = ai_enhanced`
- 不额外提示，正常展示

#### `source = rule_based`
- 展示浅色提示条
- 文案：已先为你生成一版基础可编辑行程

#### `source = fallback_template`
- 展示更明确提示条
- 文案：当前地区数据较少，先为你生成参考版

#### `failed`
- 展示失败页
- 主按钮：重新生成
- 次按钮：返回修改参数

### 7.6 日志与监控要求

虽然用户只看到产品态，但系统内部必须能记录完整异常上下文，至少包括：

- 请求 ID
- 目的地数量
- 天数
- 候选池覆盖度
- 当前生成等级（`strong / medium / weak`）
- AI 是否调用成功
- 校验是否通过
- 最终返回来源（增强版 / 骨架版 / 模板版 / 失败）
- 失败阶段
- 失败原因码

这样后续才能基于真实数据去优化，而不是只靠人工复现问题。

## 8. 本轮设计落地结论

本次 `v1` 设计的核心不是“把行程生成做得更聪明”，而是先把它做成一个稳定的产品系统：

- 规则骨架负责保底
- AI 增强负责上限
- 统一校验负责阻止坏结果流出
- 分层降级负责保证尽量给到用户可用结果
- 前端状态与提示负责把复杂系统转换成用户可理解的体验
